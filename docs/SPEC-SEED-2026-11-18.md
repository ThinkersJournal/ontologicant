# OntologicAnt: seed of the spec (PM draft of 2026-11-18, for the lane to expand and CireSnave to mark up)

Facts are marked **[said]** (CireSnave) or **[PM]** (the PM's proposal). Nothing here is verified against the literature or the crate ecosystem:
that survey is the lane's first job.

## 1. What it is
- **[said]** A set of comprehensive tool libraries covering the entire field of ontology (what exists, and how kinds and things relate) and its analysis.
- **[said]** Toolsets that AnalysAnt's lenses use, not the lenses themselves; other projects may depend on them too.
- **[said]** When a project needs a tool in this field, the tool is built here and used as a dependency.

## 2. Scope [PM]
- entities, kinds and categories; instances versus types; identity and individuation criteria
- parthood and composition (mereology); relations and their properties; taxonomies and hierarchies
- upper and domain ontologies as references; ontology alignment (matching structures across different webs of knowledge)
- consistency of an ontology; entity resolution and aliasing

## 3. First tool candidates [PM]
- a small ontology model: entities, kinds, relations, constraints
- alias and entity resolution inside a bounded domain
- taxonomy and part-of queries
- ontology alignment: a translator between two graphs whose internal structures differ (SageAnt's cross-graph addressing, X4 and X5)
- ontology consistency checks

## 4. Consumers [PM]
- AnalysAnt (the ontological lens, `analysant-ontological`)
- SageAnt (cross-graph matching and typed links)

## 5. Principles [PM]
- Generic over any use of the tool type (CireSnave 2026-11-18: "tools should be built to be generic over any use of that tool type and not specific to the individual consumer"): a consumer's needs are requirements and test cases, never the shape of the API; a tool must serve every plausible use of its kind.
- Deterministic first: rules, tables and data packs before any model; a model, if ever, is an optional escalation behind a trait. No model inside the core.
- Explainable: every verdict carries its reasons, so a human can check it.
- Small, separate crates inside one project: one version number for the project; a core of shared types plus one crate per tool family.
- Language as data: nothing hard-coded to English; Rust is the second language so text can be checked against code.
- Safe Rust (`#![forbid(unsafe_code)]`), standard-library-only core where possible, permissive-licence dependencies only.
- Every claim in a README or doc is earned: built, tested, and checked against the code.

## 6. Before any code (the lane's first job)
1. Survey: what already exists in the Rust ecosystem and in the literature for each tool family (read the crates and the papers; list what was read and what was only seen in a search result). Reuse over rebuild where a good, permissively licensed crate exists, with its licence and credit kept.
2. Write `docs/SPEC-STEP1.md`: scope, non-goals, the first three tools with API sketches, the seam with each consumer, what the first consumer needs and when, decisions that need CireSnave (`[ASK]`), and what is unverified.
3. Open ONE PR with it. No code until CireSnave has read the spec.

## 7. Foundation tools: CireSnave approved BUILDING these (2026-11-18) [PM proposal of what they are]
CireSnave asked whether there are basic tools almost anything needing this field would need, and said "If so, we can go ahead and build those." The PM's answer is below; the lane confirms or corrects it in its survey. Each tool is generic over any use of its kind.

1. **Relation graph**: a labelled, directed multigraph of entities with stable identifiers and a documented serialisation, an in-memory reference store, queries and neighbourhoods.
2. **Kinds and relations**: taxonomy (is-a) with closure and cycle detection, part-of (mereology), and declared relation properties (transitive, symmetric, inverse, functional) with the closures they imply.
3. **Identity**: alias tables, canonical identifiers, equivalence classes with merge and split that keep provenance and can be undone.
4. **Constraints and consistency**: disjointness, cardinality and domain/range checks that return the reasons for a violation, not just a flag.

Build order: survey first (reuse a good permissive crate as a dependency where one exists, with its licence and credit), then `docs/SPEC-STEP1.md` with the API of these four, then the tools as one PR per day, red-first tests with sabotage, no model in the core. CireSnave does not need to read the spec before the foundation tools are built; the spec PR is for his review as it happens.
Shared substrate question (settle with the two sibling lanes in your specs, do not each build your own copy): stable identifiers, a provenance record, a reason trace and the data-pack format are needed by all three; the PM's proposed dependency order, to avoid cycles, is SemanticAnt (text and data packs) <- OntologicAnt (graph and identity) <- EpistemologicAnt (evidence, justification), with AnalysAnt on top of all three. The PM decides after reading the three specs.
